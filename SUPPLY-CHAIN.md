# holt — supply-chain evidence

Everything on this page is something **you** can check, on the copy you installed, without
contacting the vendor and mostly without a network. That is the point: a vendor's assurance about a vendor's
CI is a claim. Evidence you can re-run is not.

```
holt audit                 # integrity + every capability this installation holds   (offline)
holt audit --json          # the same, machine-readable, exit 1 on any failure
```

---

## 1. Verify what you installed

### 1a. Integrity — offline, no network, no account

```console
$ holt audit
holt audit   holt 0.3.1 · 65 files
  /usr/lib/node_modules/holt
  tree digest  3996b36bb7922813feed6e06da605b5a3da90b0d03f52beb5586156b0e69589a

  ✓ the installed files match the manifest that shipped with them
  ✓ the detector can still see the code it is judging
  ✓ every shipped file holds only the capabilities it declares
  ✓ network egress matches the declared destinations
  ✓ no networked git verb is reachable, with or without the mutation opt-in
  ✓ every external binary the package can execute is declared, including the ones named by a variable
  ✓ every environment variable read is declared

  7/7 checks passed.
```

`MANIFEST.sha256` ships inside the package and lists a SHA-256 for every other shipped file.
`holt audit` recomputes all of them. A modified file, a deleted file, an **added** file, a
missing manifest or an unparseable one are each a **failure with a non-zero exit code** — never a
pass with a note. The manifest cannot cover itself; that is what §1b is for.

The **tree digest** is one SHA-256 over the whole manifest. It is the single number to compare
against an attestation, to paste into a ticket, or to diff between two machines that are supposed
to be running the same thing.

### 1b. Authenticity — who built this, from which commit

Integrity says the bytes are self-consistent. It cannot say who produced them. That comes from a
Sigstore provenance attestation generated by the release workflow, which needs no long-lived key
anywhere:

```console
# The published tarball, verified against the workflow and commit that built it
$ gh release download --repo Raed2180416/holt --pattern 'holt-0.3.1.tgz'
$ gh attestation verify holt-0.3.1.tgz --repo Raed2180416/holt
```

`gh attestation verify` prints the repository, the workflow file, the commit SHA and the runner
that produced the artefact. If any of those is not what you expect, the package is not ours,
whatever the version number says.

**Air-gapped?** Download the attestation bundle on a connected machine and carry it in:

```console
$ gh attestation download holt-0.3.1.tgz --repo Raed2180416/holt   # writes a .jsonl bundle
$ gh attestation verify holt-0.3.1.tgz --repo Raed2180416/holt \
    --bundle sha256:<digest>.jsonl --custom-trusted-root trusted_root.jsonl
```

Offline verification with `--bundle` has known rough edges in some `gh` versions
([cli/cli#10059](https://github.com/cli/cli/issues/10059)). If it fails for you, §1a still works
with no network at all, and `holt audit --require-signature` is the intended air-gapped path once
a release key is pinned — see §5.

## 2. SBOM

Two formats ship with every release, generated by `npm sbom` — npm's own native generator,
reading the lockfile npm itself resolved. No custom SBOM generator — the package manager's own output is more authoritative
than a third-party tool.

| file | format | why it is here |
|---|---|---|
| `holt.cdx.json` | **CycloneDX 1.5** (ECMA-424) | **primary.** Native VEX support, the format security tooling — Dependency-Track, Snyk, Trivy, Grype — ingests best, and the one CRA-aligned tooling has standardised on. |
| `holt.spdx.json` | **SPDX 2.3** (the ISO/IEC 5962:2021 lineage) | for procurement and licence-compliance workflows that require SPDX by policy. |

Both, rather than one, because the marginal cost is a second `npm sbom` invocation and the
alternative is an argument with whichever reviewer wanted the other one.

### What the SBOM says, and the trap it avoids

```
required runtime dependencies: 0
optional (installed by default, removable with --omit=optional): 99
```

**holt has zero required runtime dependencies.** Everything in the SBOM is an
`optionalDependency` — `@modelcontextprotocol/sdk` (for `holt mcp`) and `jscpd` (for
`holt duplicates --deep`) — plus their transitive graph. If your policy is to minimise
third-party code:

```console
$ npm install -g https://github.com/Raed2180416/holt/releases/latest/download/holt.tgz --omit=optional     # a genuinely zero-dependency install
```

`holt doctor` will tell you which optional capabilities are unavailable, by name. Nothing else
changes; CI proves the degraded path on every commit.

> `npm sbom` run plainly on a developer machine describes **node_modules as installed**, which on
> any machine that ran `npm ci` is the *dev* tree — 187 components including Stryker, Babel and
> Express, none of which ship. `scripts/gen-sbom.mjs` passes `--package-lock-only --omit dev` and
> **fails the build** if a dev-only package appears, if any component lacks a purl, or if the
> version disagrees with `package.json`. An SBOM that describes the wrong tree does not just fail
> to help — it generates vulnerability tickets against software the vendor does not ship.

## 3. Build provenance

| property | status |
|---|---|
| SLSA version | v1.0 build track |
| **Build level achieved today** | **Build L2** — GitHub-hosted runner, provenance generated by GitHub's control plane and signed with a Sigstore short-lived certificate bound to the workflow's OIDC identity. The tenant cannot forge it. |
| Build L3 | reachable, not claimed. It requires the build to run inside a **reusable workflow** so build logic is isolated from the caller. `.github/workflows/release-artifact.yml` is a single-repo workflow today, so the published level is L2. |
| Predicate | SLSA Provenance v1 in an in-toto Statement |
| Transparency log | Sigstore public-good instance (Rekor) |
| Release attestation | `gh attestation verify` on the release tarball, bound to the workflow's OIDC identity |

The published level is what can be defended. A vendor claiming L3 from a plain workflow is telling you
they have not read the specification, which is itself a useful signal about the rest of their
answers.

## 4. What holt reads, writes and sends

This section is **checked against the code on every audit run** — `src/supply-chain.mjs` holds
the declaration, `holt audit` compares it to the bytes on disk, and a test in
`test/unit/supply-chain.test.mjs` fails if this document and that declaration disagree. It cannot
rot into a stale marketing page, because a stale entry fails the build.

### Sends — one destination, and only when you ask

| when | to where | what is sent |
|---|---|---|
| `holt setup`, or `holt doctor --install` | `https://github.com/universal-ctags/ctags-nightly-build/releases/download/…` | **nothing.** An unauthenticated GET of a pinned public release asset. No body, no query string, no headers, no identifiers. The response is checked against a SHA-256 pinned in `src/toolchain.mjs` and **refused** on mismatch. Avoid it entirely by installing `universal-ctags` from your own package manager. |

### The indirect path, stated because a true sentence can still mislead

`holt setup` and `holt doctor --install` can also run **your package manager** —
`apt-get` / `dnf` / `pacman` / `brew` / `winget`, prefixed with `sudo` on Linux — to install
`universal-ctags` or `ripgrep`. holt opens no socket doing that, so nothing in the capability
ledger flags it; the package manager reaches the network on holt's behalf.

It only happens after holt **prints the exact command**, says so if it needs sudo, and requires
you to type `y` (or pass `--yes`). It is the only path in the product that elevates privilege,
and no analysis, scan, hook, MCP call or git action ever runs elevated.

The indirect path is disclosed here because a true sentence can still mislead: `sh` was
described as "backend probes and `holt verify --run`" and stopped there — every word true, and the
reader would still have finished the paragraph with a wrong picture. `holt audit --json` reports
it under `statement.indirectNetwork`.

No telemetry. No analytics. No crash reporting. No update check. **No licence call-home** —
entitlement is an offline Ed25519 signature check (`src/license.mjs`), which is why holt works
on an air-gapped machine and why a licence cannot be revoked remotely (it is expressed as short
expiry instead).

Two independent things make that checkable rather than promised:

- **The capability ledger.** Every shipped file is classified by what it can reach —
  `network`, `process`, `eval`, `filesystem`. Exactly one file holds `network`, and it is the
  installer above. Adding `import net from 'node:net'`, a bare `require('https')`, a dynamic
  `import('node:http')` or a bare `fetch(` anywhere else fails the audit.
- **git cannot reach the network either.** holt drives git through an argv allowlist, and every
  networked verb — `fetch`, `push`, `pull`, `clone`, `ls-remote`, `remote`, `submodule`,
  `daemon`, `credential`, the `http-*` helpers, `p4`, `svn` — is outside it, with and without the
  mutation opt-in. `holt audit` proves this by *calling* the classifier, not by reading a list,
  and it also proves `git rev-parse` is still allowed so that "nothing reachable" cannot be a
  blanket deny masquerading as a result.

### Executes

`git`, and — only if present and only for the feature that needs them — `jj`, `ctags`, `enry`,
`rg`, `jscpd`, `tar`, `sh`, `holt`, `go`, `mount`, `where`. Every one is listed in `holt audit --json`
under `checks[].detail`, including the call sites where the executable is a **variable** rather than a
literal, which is the half a string scan cannot see.

Three of those are worth stating plainly rather than burying:

- **`holt verify --run "<cmd>"` executes the command you give it.** That is the feature: it runs
  *your* test suite against a speculative merge. It runs nothing you did not type.
- **`sh -c "command -v <tool>"`** is used to probe for optional backends. On Windows, `where <tool>`
  is used instead (it is the Windows equivalent of `command -v`).
- **`go install github.com/go-enry/enry@latest`** is offered by `holt setup` when Go is available
  and enry is missing. `mount` is used on macOS/Unix to detect network filesystems (NFS/SMB/SSHFS)
  for timeout escalation. On Windows, `powershell` `-Command Expand-Archive` extracts the ctags zip
  (listed as a dynamic call site in `bin/install-ctags.mjs`, after checksum verification).

### Reads

The git repository you point it at, plus its own config and cache paths. Nothing else.

### Writes

holt **never writes to the repository it inspects** — that is the core promise, enforced in
`src/git.mjs` and proven by `test/unit/safety.test.mjs`. The single exception is an
*unreferenced* git object from `merge-tree --write-tree`, which git's own gc reclaims and which
`--strict-read-only` removes entirely.

Everywhere else it can write:

| path | put there by | notes |
|---|---|---|
| `$XDG_CONFIG_HOME/holt/license` | `holt license activate` | mode 0600, opened `O_NOFOLLOW` |
| `$GIT_COMMON_DIR/holt/journal.jsonl` | every mutating action | append-only, inside the git dir, never in the working tree |
| `$HOLT_HOME` (or `$XDG_DATA_HOME/holt`) | `holt setup` | the ctags binary it installed |
| the path you pass to `--html` | `holt graph --html <file>` | you named it |
| a scratch dir under `$TMPDIR` | `holt verify`, the jscpd backend | created and removed by the command |
| agent host config files in the repo | `holt integrate` | the entire purpose of that command; it prints what it will write |

### Environment variables read

`AI_AGENT`, `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_HOST_SESSION_ID`,
`CURSOR_TRACE_ID`, `GITHUB_HEAD_REF`, `HOLT_ACTOR`, `HOLT_ACTOR_SESSION`, `HOLT_AUDIT_SIGNER`,
`HOLT_AUDIT_SIGNING_KEY`, `HOLT_CTAGS_OPTIONS`, `HOLT_HOME`, `HOLT_HOOK_FAIL_OPEN`,
`HOLT_LICENSE`, `HOLT_TMPDIR`, `JJ_CONFIG`, `LOCALAPPDATA`, `LOGNAME`, `NO_COLOR`, `OPENCODE`,
`PATH`, `TERM`, `TMPDIR`, `USER`, `USERNAME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`.

None are transmitted, because there is nowhere to transmit them to. A **computed** read
(`process.env[name]`) anywhere in the package would fail the audit rather than being quietly
skipped, precisely so this list cannot be silently incomplete.

## 5. What is not in place yet, and exactly what it needs

Stated here rather than omitted, because a security page that lists only what is done is not a
security page.

| gap | what it needs | who must do it |
|---|---|---|
| **Detached manifest signature activation** — the public key is pinned in `RELEASE_PUBLIC_KEYS_B64` and the signing step is in `release-artifact.yml`, but the private key must be stored as the repository secret **`HOLT_RELEASE_SIGNING_KEY`** (PKCS#8 PEM) for the workflow to sign releases. Until then, the signing step skips gracefully and `holt audit --require-signature` reports `unavailable`. | Store the private half of the Ed25519 key pair as the repository secret `HOLT_RELEASE_SIGNING_KEY`. The public key is already in `src/supply-chain.mjs`. | repository owner |
| **SLSA Build L3** | Move the build into a reusable workflow so build logic is isolated from the caller. | maintainers |

Generating the pair, for the record — run it on a machine you trust and never commit the private
half:

```console
$ openssl genpkey -algorithm ed25519 -out holt-release.pem
$ openssl pkey -in holt-release.pem -pubout -outform DER | base64 -w0   # -> RELEASE_PUBLIC_KEYS_B64
```

## 6. Reporting

Security reports go through
[GitHub Security Advisories](https://github.com/Raed2180416/holt/security/advisories/new).
Acknowledgement within 72 hours, substantive reply within 7 days. See `SECURITY.md` for scope,
and `docs/SECURITY-QUESTIONNAIRE.md` for the vendor-review answers a procurement team will ask
for.

**If you observe holt make a network call other than the one in §4, that is a vulnerability
— please report it.**
