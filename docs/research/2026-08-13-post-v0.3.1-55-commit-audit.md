# Holt post-v0.3.1: 55-commit investor and technical audit

**Audit date:** 2026-08-13
**Compared:** public tag `v0.3.1` → repository `main` at `e142f73f`
**Scope:** every one of the 55 reachable commits after `v0.3.1`; current uncommitted work is
excluded from the commit counts and assessed separately before release.

## Bottom line

The 55 commits are real engineering progress, but they are not 55 units of market progress.
They predominantly harden release integrity, portability, evaluation validity, and public
positioning. That is valuable for a product whose promise is safe destructive authority. It also
reveals the uncomfortable gap: **the best current Holt is still source-only, while the install path
an investor or design partner reaches is the older `v0.3.1` artifact.** No customer traction can be
inferred from this history.

The investor-positive reading is that Holt is not a prompt wrapper: the history contains concrete
cross-platform safety repairs, recoverability fixes, fail-closed CI, task-scoped coordination, and
serious release provenance work. The investor-negative reading is that the founder has spent a
large stabilization tail inside the repository without yet converting it into a current release,
outside installations, repeated use, or a budget-owning customer.

**Conviction:** stop counting commits. Promote a current, independently installable artifact only
after its exact gates pass, and then spend the next proof window on witnessed external workflows.
The next fundable milestone is not commit 56; it is one outside operator changing a consequential
cleanup or landing decision because of Holt and returning to use it again.

## The uncomfortable findings

### 1. Product progress is stranded behind the release boundary

The current README correctly warns that the source checkout and latest release may differ, but the
commercial reality is harsher: anyone using the stable release URL evaluates `v0.3.1`, not this
55-commit body of work. Until a new tag binds source SHA, tests, package, checksums/signature,
installed smoke, and release notes, the improvements are unavailable proof—not shipped product.

### 2. The stabilization tail is large

Eight explicitly labelled fix commits and many test/CI follow-ups close serious classes: hostile
Git filters, index-flag reads, path aliases, Windows behavior, quarantine lock retention, and
journal locking. These are the right bugs to fix in a safety tool. Their density immediately after
`v0.3.1` means the next release should be treated as a release candidate requiring exact artifact
verification, not casually described as production-ready.

### 3. One change is too large for easy review

`faa3f79b` changes 70 files (+5,988 / -1,790) across release, product, tests, docs, and launch
surfaces. Its work may be correct, but a multi-domain commit of that size weakens causal review,
bisectability, and investor diligence. Do not rewrite history now; improve the next PR discipline:
one safety invariant, its failing reproducer, its repair, and its evidence in a reviewable slice.

### 4. CI repair churn is evidence of rigor and of complexity

The repeated Windows, namespace, sandbox, Pages, action-pinning, and manifest commits show a team
that follows failures through. They also show that Holt's proof/release machinery is itself a large
system with significant maintenance cost. That cost is justified only if it unlocks trusted use.
It becomes founder risk if it continuously consumes the customer-discovery window.

### 5. Repository governance lags the release machinery

Live GitHub inspection on 2026-08-13 found release immutability enabled, Actions restricted with
SHA pinning required, a `release` environment limited to `v*` tags, and both release secrets
present. However, `main` had no branch protection and the repository had no rulesets. This makes
the cryptographic release graph stronger than the ordinary merge-control boundary. Add protection
only after the universal lightweight trust check is present on the branch and its exact required
check name has been observed in a real pull request.

### 6. None of this is traction

Branding, launch posts, an application deck, issue templates, green CI, tests, and a sophisticated
release graph can improve conversion and trust. They do not establish a customer, a recurring
workflow, a paid evaluation, avoided loss, or willingness to pay. The absence of marketing to date
explains why traction has not been attempted; it does not allow traction to be assumed.

## Where Holt is lagging now

Ordered by company risk, not implementation novelty:

1. **Outside usage and distribution.** No qualified conversation/install/repeat-use denominator is
   established. Marketing absence explains this; it does not reduce its urgency.
2. **Current public artifact.** The 55 commits are not in the latest release. A new release must be
   promoted through the existing evidence graph, not uploaded by hand.
3. **Action-seam integration proof.** Many host adapters are contract-tested, but broad live host
   deny/upgrade/uninstall evidence is incomplete.
4. **False-hold economics.** Fail-closed safety is correct, but a tool that asks too often will be
   bypassed. Real workflow denominators are needed, including negative controls.
5. **Mutation atomicity.** Integration install/uninstall/reconcile paths need content/inode-bound
   check-and-act semantics so a concurrent user edit cannot be overwritten or deleted.
6. **Adversarial work budgets.** Glob matching must have a total deterministic operation budget,
   not merely a linear algorithm per candidate, so large candidate sets cannot turn the guard into
   an availability failure.
7. **Main-branch governance.** No protection/ruleset currently binds merges to the trust lane.
8. **Commercial proof.** The paid repository code, pricing model, buyer, procurement boundary, and
   willingness to pay remain hypotheses.

## Current candidate remediation after the 55-commit anchor

The findings above audit committed history through `e142f73f`; they do not count the working
candidate as a fifty-sixth historical commit. Before promotion, that candidate closes three
specific boundaries identified during this review:

1. **Integration file transactions and receipt authority.** Writes and removals now operate on a
   stable regular-file observation, retire the exact observed inode into recovery, publish
   exclusively, and preserve concurrent replacements. Current project receipt entries bind
   SHA-256, device, inode, size, ctime, and worktree identity to the transaction-returned
   publication token. Legacy hash-only receipts remain useful for reproducibility classification
   but cannot authorize whole-file deletion. Receipt publication is compare-and-swap merged and
   re-verifies authored identities before and after publication. A reproduced byte-identical inode
   replacement was deleted before this repair and survives afterward.
2. **Multi-worktree uninstall receipt lifecycle.** The CLI carries one initial receipt snapshot
   across adapter removal in every linked worktree and clears only that exact receipt transaction.
   A concurrent re-integration can no longer be erased by a final pathname-only cleanup.
3. **Total glob work budget.** Bracket parsing and candidate traversal consume one shared bounded
   budget. Overflow returns conservative evidence rather than allowing a large candidate set to
   turn individually linear matching into unbounded aggregate work.

Focused candidate evidence at the review boundary includes 79/79 integration-upgrade cases, 6/6
moved-repository cases, 20/20 adversarial receipt-race iterations, 6/6 receipt mutants killed, and
the glob adversarial tests and mutants. These are implementation evidence, not a substitute for
the full frozen-candidate suite, hosted matrix, exact installed artifact, or outside usage. The
candidate remains unpromoted until those later gates complete.

Two explicit residual boundaries remain: legacy receipts may leave safe residue until a new
identity-bound lifecycle creates current authority, and empty-directory cleanup is still based on
recorded name plus emptiness rather than directory inode. Neither grants deletion authority over
file bytes, but both should remain visible in future transaction work.
